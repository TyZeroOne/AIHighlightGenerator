# Этап 1: Каркас архитектуры

## Цель этапа

Создать пустой, но **живой** скелет приложения:

1. Слои и правило зависимостей между ними — с автоматической проверкой.
2. Домен: сущности и объекты-значения, вокруг которых крутится всё остальное.
3. Порты — интерфейсы, через которые ядро говорит с внешним миром.
4. Реестр плагинов — механизм расширения без правки ядра.
5. Инфраструктура: конфиг, логирование, БД, миграции, DI-контейнер.
6. FastAPI, отвечающий на `/health`, и Celery, выполняющий задачу `ping`.
7. Docker Compose, поднимающий всё это одной командой.

Пока это не работает с видео. Но именно на этот каркас будут навешиваться
все девять следующих этапов — поэтому каждое решение здесь стоит дороже,
чем кажется: ошибку в границах слоёв на Этапе 7 исправлять будет уже поздно.

---

## Теория

### Clean Architecture: правило одной стрелки

Главная идея умещается в одну фразу: **зависимости направлены внутрь, к домену,
и никогда наружу**.

```
     снаружи (меняется часто)          внутри (меняется редко)

  FastAPI, Celery ──▶ Сценарии ──▶ Домен ◀── Порты ◀── FFmpeg, Whisper, Claude
       (доставка)      (что делаем)  (что это)          (реализации)
```

Стрелка «внутрь» — это направление зависимости, а не направление вызова.
FFmpeg **вызывается** сценарием, но **зависит** от домена — потому что реализует
интерфейс, объявленный в ядре.

**Зачем такая гимнастика.** Возьмём конкретный вопрос из нашего проекта:
«как заменить faster-whisper на другой движок распознавания?»

| Подход | Что придётся менять |
|---|---|
| Прямые вызовы (`from faster_whisper import WhisperModel` в конвейере) | Каждое место, где вызывался Whisper. Плюс тесты, которые теперь тянут модель на 3 ГБ |
| **Clean Architecture** (наш выбор) | Один новый класс, реализующий `Transcriber`, и одна строка в контейнере |

То же самое отвечает на вопросы «как добавить YouTube», «как тестировать без БД»,
«как подменить LLM на заглушку». Все они решаются одинаково, потому что
причина одна: **детали реализации не должны просачиваться в ядро**.

**Цена.** Больше файлов и один лишний уровень косвенности. На проекте из
трёх скриптов это чистые накладные расходы. На проекте, где к десятому этапу
будет 15 плагинов, три источника видео и два хранилища — это единственный
способ не утонуть.

**Альтернативы, которые мы отвергли:**

| Архитектура | Когда хороша | Почему не наш случай |
|---|---|---|
| «Всё в одном пакете» | Скрипты, прототипы, < 20 файлов | Ко второму этапу конвейер перестал бы влезать в голову |
| Классическая слоёнка (`controllers → services → repositories`) | CRUD-приложения | Зависимость идёт сверху вниз до самой БД: домен знает про SQLAlchemy, тесты требуют базу |
| Микросервисы | Разные команды, разный масштаб нагрузки | Один разработчик, один конвейер. Сеть между этапами добавила бы отказов, не добавив пользы |

Мы выбрали **модульный монолит**: одно приложение, жёсткие границы внутри.
Если позже понадобится вынести `vision` в отдельный сервис, границы уже прочерчены.

### Три слоя чистоты

В проекте не два уровня «внутри/снаружи», а три, и различать их важно:

| Слой | Что можно импортировать | Пример |
|---|---|---|
| `core/domain`, `core/ports` | **только стандартную библиотеку** | `TimeRange`, `Transcriber` |
| `core/usecases` | домен и порты | «загрузить видео», «запустить анализ» |
| всё остальное | что угодно | `FFmpegCutter`, `ClaudeProvider`, роутеры |

Самый строгий слой — самый внутренний. Это не эстетика: `core/domain`
импортируется **всеми**, и если он потянет за собой `torch`, то API-контейнер
будет грузить 2 ГБ CUDA-библиотек ради того, чтобы ответить на `/health`.

> **Почему `pydantic` тоже запрещён в домене**
>
> Соблазн велик: Pydantic даёт валидацию бесплатно. Но он привязывает домен
> к конкретной библиотеке сериализации, а его модели изменяемы по умолчанию
> и валидируются заново при каждом создании. В домене мы используем
> `@dataclass(frozen=True, slots=True)` с ручной проверкой в `__post_init__`:
> примерно та же строгость, ноль зависимостей, и объекты дешевле.
>
> Pydantic при этом активно используется — но в `core/config.py`
> и в `api/schemas` — там, где он на своём месте: на границе с внешним миром.

### Protocol против ABC: почему интерфейсы объявлены именно так

В Python есть два способа задать интерфейс, и разница между ними — не стилистическая.

```python
# Вариант 1: абстрактный базовый класс
class Transcriber(ABC):
    @abstractmethod
    async def transcribe(self, audio): ...


class WhisperTranscriber(Transcriber):  # ← обязан импортировать ядро
    ...


# Вариант 2: Protocol (наш выбор)
class Transcriber(Protocol):
    async def transcribe(self, audio): ...


class WhisperTranscriber:  # ← ничего не наследует
    async def transcribe(self, audio): ...
```

При ABC адаптер **обязан наследоваться**, то есть **импортировать ядро**.
Стрелка зависимости всё ещё направлена внутрь, так что формально всё в порядке.
Но появляется практическая проблема: сторонний плагин из чужого пакета обязан
знать про нашу иерархию классов и версию нашей библиотеки.

`Protocol` проверяет соответствие **структурно**: если у класса есть метод
`transcribe` с подходящей сигнатурой — он подходит, и неважно, откуда он взялся.
Проверку делает `mypy` на этапе типизации, а не интерпретатор в рантайме.

**Что мы за это платим:** ошибка «забыл реализовать метод» всплывает при
запуске `mypy`, а не при `import`. Поэтому `mypy --strict` в DoD этапа — не
формальность, а замена той страховки, которую при ABC давал бы интерпретатор.

Эта же причина объясняет, почему `supports()` в `SourceProvider` объявлен
как `@classmethod`: резолвер должен спросить «ты умеешь обработать этот URI?»
**до** создания экземпляра — создание может требовать ключей API и сетевого клиента.

### Домен и ORM — почему это разные классы

Соблазнительно объявить один класс `Scene`, навесить на него SQLAlchemy
и использовать везде. Так работает паттерн **Active Record** (Django ORM,
Rails). Мы этого не делаем.

| | Active Record (один класс) | Domain + ORM (наш выбор) |
|---|---|---|
| Кода | Меньше | Больше: нужен маппинг |
| Тест домена | Требует БД или сложных моков | Просто создаёшь объект |
| Смена БД | Переписать всё | Переписать репозитории |
| Случайный запрос в БД | `scene.video.user.email` — три скрытых SELECT | Невозможен: у домена нет соединения |
| Неизменяемость | Невозможна | `frozen=True` |

Последние два пункта решающие. **Ленивая загрузка** в асинхронном коде —
источник самых неприятных багов: обращение к полю за пределами сессии
падает с `MissingGreenlet`, причём в проде и под нагрузкой. Мы отключаем её
принудительно (`lazy="raise"` во всех связях): если кто-то попытался
обратиться к незагруженной связи, он получит внятную ошибку сразу,
а не таинственный сбой через месяц.

**Цена решения честная:** на Этапе 2 придётся писать функции
`orm_to_domain` / `domain_to_orm`. Это скучно. Но это единственное скучное
место, а взамен весь домен тестируется без базы — и все 127 тестов этого
этапа проходят за секунды именно поэтому.

### Реестр плагинов и топологическая сортировка

Требование из ТЗ: «анализаторы подключаются через расширяемый механизм плагинов».
Разберём, как это устроено, потому что это сердце проекта.

**Наивный вариант**, с которого начинают почти все:

```python
def analyze(scene):
    features = {}
    features.update(analyze_loudness(scene))
    features.update(analyze_motion(scene))
    features.update(analyze_faces(scene))  # ← добавление признака = правка этой функции
```

Проблемы: добавление признака требует правки ядра; отключить анализатор можно
только комментированием; порядок задан вручную; параллелить нечего.

**Наш вариант** — реестр с декларацией зависимостей:

```python
@register_analyzer
class MotionAnalyzer:
    key = "vision.motion"
    requires = frozenset({"artifact.video"})  # что нужно на входе
    produces = frozenset({"vision.motion.mean"})  # что появится на выходе
    cost = 3  # относительная стоимость
```

Планировщик `build_plan()` раскладывает анализаторы по **слоям**:

```
доступно: {artifact.video, artifact.audio}

слой 0: [vision.motion, audio.loudness, audio.pauses]   ← всем хватает входа
        → добавилось: vision.motion.mean, audio.loudness.peak, ...
слой 1: [speech.rate_delta]                              ← нужен был speech.rate.wpm
```

Внутри слоя анализаторы независимы → в Celery это `group()`, они идут параллельно.
Слои идут строго последовательно.

Алгоритм — **топологическая сортировка по слоям** (алгоритм Кана):
> Пока остались незапланированные анализаторы: взять все, чьи `requires`
> уже удовлетворены; если таких нет — значит, цикл или недостающее сырьё,
> сообщить об этом внятно; иначе добавить их слоем и пополнить множество доступного.

Три полезных свойства достаются бесплатно:

1. **Циклы обнаруживаются** — `a` требует `b.value`, `b` требует `a.value` → понятная ошибка вместо зависания.
2. **Недостающее сырьё диагностируется** — у видео нет аудио, анализатор громкости не планируется, и в ошибке написано, чего именно не хватило.
3. **Порядок внутри слоя оптимизируется** — дорогие анализаторы ставятся первыми, чтобы не оказаться «хвостом», растягивающим этап.

**Три уровня расширения** — по возрастанию независимости:

| Уровень | Как | Кому |
|---|---|---|
| Декоратор `@register_analyzer` | Файл внутри репозитория | Нам, на Этапе 5 |
| Entry point `highlight.analyzers` | Отдельный пакет на PyPI | Стороннему разработчику |
| `ANALYZERS_DISABLED` в конфиге | Переменная окружения | Администратору |

Третий уровень часто забывают, а он важнее первых двух: возможность **выключить**
сломавшийся анализатор без пересборки образа спасает прод.

> **Плата за реестр: глобальное состояние.**
> `_ANALYZERS` — словарь уровня модуля, то есть глобальная переменная со всеми
> её недостатками. Тест, зарегистрировавший фейковый анализатор, испортил бы
> следующий. Поэтому в `conftest.py` есть автоматическая фикстура, вызывающая
> `clear_registries()` после каждого теста. Альтернатива — передавать реестр
> объектом через все вызовы — усложнила бы декоратор до неузнаваемости.

### Композиционный корень и внедрение зависимостей

Если ядро работает с интерфейсами, кто-то должен подставить реализации.
Это делает **композиционный корень** — единственное место, где встречаются
абстракция и конкретика (`core/container.py`).

```python
@cached_property
def transcriber(self) -> Transcriber:
    return FasterWhisperTranscriber(model=self.settings.whisper_model)
```

Три решения внутри этих трёх строк:

**Почему `cached_property`, а не создание в `__init__`.** API-процессу не нужна
модель Whisper, а CPU-воркеру не нужен клиент LLM. Ленивое создание означает,
что ресурс появляется при первом обращении — и не появляется вовсе, если
не понадобился. Модель Whisper весит 3 ГБ; загрузить её в API-контейнере
«на всякий случай» — потерять 3 ГБ RAM на каждой реплике.

**Почему свой контейнер, а не библиотека DI.** Существуют `dependency-injector`,
`punq`, `wired`. Они дают автосвязывание по типам и области видимости.
Нам это не нужно: зависимостей около десяти, все создаются в одном месте,
все явно видны. Библиотека добавила бы магию и ещё одну зависимость ради
экономии тридцати строк. Если контейнер вырастет до сотни свойств —
пересмотрим; пока KISS.

**Почему синглтон на процесс, а не глобальные функции.** Глобальные функции
(`get_transcriber()`) невозможно подменить в тесте, не патча модуль.
Контейнер — обычный объект: тест создаёт свой, с фейками внутри.

### Конфигурация: провал на старте вместо провала через час

```python
class Settings(BaseSettings):
    score_alpha: float = 0.4
    ...

    def model_post_init(self, _):
        total = self.score_alpha + self.score_beta + self.score_gamma
        if abs(total - 1.0) > 1e-6:
            raise ValueError(...)
```

Разница между этим и `os.environ["SCORE_ALPHA"]` по месту использования:

| | `os.environ` по месту | Pydantic Settings (наш выбор) |
|---|---|---|
| Опечатка в имени переменной | `KeyError` в момент использования — возможно, через час работы | При старте процесса |
| Типы | Всё строки, конвертация руками | Автоматически, с проверкой |
| Взаимосвязи (сумма весов = 1) | Никто не проверяет | Проверяется |
| Что вообще настраивается | Надо грепать по коду | Один класс |

**Принцип: fail fast.** Некорректно настроенный процесс не должен подниматься
вообще. Худшее, что может случиться — контейнер, который выглядит здоровым,
принимает трафик, и падает только на редком пути кода.

Отдельно: `get_settings()` обёрнут в `@lru_cache`. Это даёт синглтон
(разбор `.env` один раз) и при этом остаётся тестируемым —
`get_settings.cache_clear()` возвращает всё в исходное состояние.

### Структурное логирование и сквозной `trace_id`

Один джоб проходит через API-процесс и пять Celery-задач в трёх контейнерах.
Обычный лог в такой ситуации бесполезен: события перемешаны, связать их нечем.

Решение из двух частей:

**1. Структурный формат.** Не строка, а набор полей:

```json
{"event": "task.retry", "trace_id": "0f9c…", "job_id": "3c9f…",
 "stage": "transcribe", "attempt": 2, "timestamp": "2026-08-02T10:15:04Z"}
```

Такое можно фильтровать (`trace_id = "0f9c…"`) и агрегировать
(«среднее время этапа transcribe»). Строку `"Retry 2 for job 3c9f"` — нельзя.

**2. `contextvars` вместо передачи параметром.** Альтернатива — таскать
`trace_id` аргументом через все функции — загрязняет каждую сигнатуру
в проекте. `ContextVar` автоматически наследуется вложенными вызовами
и, в отличие от `threading.local`, **корректно работает в asyncio**, где
десятки задач исполняются в одном потоке.

```python
with bind_trace(job_id=job_id, stage="transcribe"):
    ...  # всё, что залогируется внутри, включая await-вызовы, получит эти поля
```

### Celery: четыре решения, которые нельзя отложить

**Очереди по типу ресурса, а не по смыслу задачи.** Естественным кажется
разделение `queue=video`, `queue=audio`. Правильное — по тому, что задача
занимает:

| Очередь | Ресурс | Конкурентность |
|---|---|---|
| `cpu` | Процессор (ffmpeg, скоринг) | По числу ядер |
| `io` | Диск и сеть | Высокая — задачи в основном ждут |
| `gpu` | Видеопамять | 1–2, иначе VRAM кончится |
| `net` | Внешний API | 4, ограничено rate limit'ом |

Причина: задача, ждущая ответа LLM, не должна занимать слот у задачи,
считающей на GPU. Смешай их в одной очереди — и десять LLM-вызовов
заблокируют транскрипцию, ничего при этом не делая.

**`task_acks_late = True`.** По умолчанию Celery подтверждает получение
сообщения **до** выполнения. Убили воркер посреди двухчасовой транскрипции —
задача потеряна безвозвратно. С поздним подтверждением сообщение вернётся
в очередь. Плата: задача может выполниться дважды, поэтому **все задачи
обязаны быть идемпотентными** — отсюда и проверка `is_stage_done()` в домене.

**`worker_prefetch_multiplier = 1`.** По умолчанию воркер набирает пачку
задач «про запас». Для задач в миллисекунды это разумно. Для наших,
идущих минутами, — катастрофа: один воркер забирает восемь задач,
выполняет их последовательно, а три других простаивают.

**Только JSON, никакого pickle.** `pickle` умеет сериализовать что угодно —
и именно поэтому опасен: сообщение из брокера при десериализации **исполняется
как код**. Доступ к Redis превращается в удалённое выполнение кода.
JSON ограничен примитивами, и это ограничение здесь — защитный механизм.

### Миграции: почему первая написана вручную

Alembic умеет генерировать миграции автоматически (`--autogenerate`),
сравнивая модели с состоянием БД. Первую миграцию мы написали руками, потому что:

- автогенерация **не умеет создавать нативные enum-типы PostgreSQL** в правильном
  порядке — она создаёт таблицы, ссылающиеся на ещё не существующие типы;
- она **путает частичные индексы** (`postgresql_where`), а у нас их три,
  и на них держится идемпотентность;
- для автогенерации нужна живая БД, а миграция должна существовать до неё.

Дальше по проекту автогенерация используется, но её вывод всегда читается глазами.

Отдельная тонкость — **значения enum дублируются в файле миграции**. Это выглядит
нарушением DRY, но это осознанно: миграция обязана быть самодостаточной.
Если завтра в `core/domain/enums.py` добавится значение, **эта** миграция должна
остаться неизменной — иначе прогон на чистой базе даст схему, отличную от продовой.

Ещё одна ловушка, которую мы обошли:

```python
SAEnum(enum_cls, name=name, values_callable=lambda e: [m.value for m in e])
```

Без `values_callable` SQLAlchemy пишет в базу **имена** членов (`SUCCEEDED`),
а не значения (`succeeded`). Обнаруживается это обычно тогда, когда кто-то
пишет `WHERE status = 'succeeded'` вручную и получает пустой результат.

### Liveness и readiness — почему это два разных эндпоинта

| | `/health` (liveness) | `/health/ready` (readiness) |
|---|---|---|
| Вопрос | «Процесс жив?» | «Готов принимать трафик?» |
| Проверяет | Ничего | БД, Redis, хранилище |
| Кто спрашивает | Оркестратор | Балансировщик |
| Реакция на провал | **Перезапустить контейнер** | **Вывести из балансировки** |

Смешать их — классическая ошибка с дорогими последствиями. Если liveness
начнёт проверять БД, то при её падении Kubernetes начнёт перезапускать
все здоровые контейнеры приложения. Нагрузка на базу от лавины
переподключений вырастет — и БД, которая могла бы восстановиться,
не восстановится. Отсюда правило: **liveness не трогает зависимости**.

Проверки в readiness идут параллельно и с общим таймаутом: последовательно
три проверки по 3 секунды дадут 9 секунд в худшем случае, и проба
балансировщика отвалится раньше, чем мы ответим.

### RFC 7807 — стандартный формат ошибки

```json
{
  "type": "https://docs.../errors/unsupported-media",
  "title": "Unsupported media type",
  "status": 415,
  "detail": "Container 'avi' is not supported. Allowed: mp4, mkv, mov.",
  "instance": "/api/v1/upload",
  "trace_id": "0f9c…",
  "code": "UNSUPPORTED_MEDIA"
}
```

Почему стандарт, а не свой формат: он заставляет отдавать **машиночитаемый
`code` рядом с человекочитаемым `detail`**. Клиент ветвится по `code`
(он стабилен), человек читает `detail` (он может меняться).
Самая распространённая ошибка API — отдавать только текст: клиенту
приходится сравнивать строки, и любая правка формулировки ломает интеграцию.

`trace_id` в теле ошибки — чтобы пользователь мог назвать его в поддержке,
а мы по нему нашли всю историю запроса. При этом наружу **не уходит ни текст
исключения, ни трейсбек**: это утечка деталей реализации, полезная атакующему.

### Тест, который охраняет архитектуру

Архитектура, держащаяся на дисциплине, разваливается на третьем месяце —
в пятницу вечером кто-то (обычно ты сам) импортирует `speech` из `vision`,
потому что «так быстрее».

Поэтому правило зависимостей проверяется тестом. Он разбирает каждый файл
в **AST** и смотрит на импорты:

```python
tree = ast.parse(path.read_text())
for node in ast.walk(tree):
    if isinstance(node, ast.ImportFrom):
        ...
```

**Почему AST, а не проверка фактических импортов в рантайме.** Импорт внутри
функции или в ветке `if TYPE_CHECKING` в рантайме может никогда не выполниться —
и нарушение останется незамеченным. AST видит исходный текст целиком.

Пять правил, которые проверяются:

1. `core.domain` и `core.ports` не импортируют тяжёлые библиотеки.
2. `core.domain` не импортирует ничего из проекта, кроме себя.
3. `core.ports` зависит только от домена.
4. Адаптеры (`vision`, `speech`, …) не импортируют друг друга.
5. Адаптеры не импортируют `api` и `workers`.

## Пошаговый разбор

### Шаг 1. `pyproject.toml` — один файл конфигурации на всё

Зависимости разделены на группы (`extras`):

```toml
dependencies = [ ... ]                 # нужно ВСЕМ процессам
[project.optional-dependencies]
api    = ["fastapi", "uvicorn", ...]   # только API
worker = ["celery", "redis"]           # только воркер
dev    = ["pytest", "ruff", "mypy"]    # только разработка
```

> **Зачем разделять, если всё равно один репозиторий**
>
> Образ API собирается с `pip install ".[api]"` и не тянет Celery.
> Образ воркера — с `".[worker]"` и не тянет uvicorn. На Этапе 4 в `worker`
> добавятся `torch` и `faster-whisper` — это ~2.5 ГБ, которых в API-образе
> быть не должно.
>
> **Альтернатива:** один `requirements.txt` на всё. Проще, но образ API
> к концу проекта весил бы 4 ГБ вместо 400 МБ, а деплой занимал бы минуты.

> **Почему `psycopg` И `asyncpg` — два драйвера к одной БД**
>
> Приложение асинхронное → `asyncpg`. Alembic синхронный → `psycopg`.
> Смешивать asyncio с миграциями незачем: они выполняются один раз при деплое,
> выигрыш нулевой, сложности много.
>
> Это, кстати, ошибка, найденная во время проверки этапа: `psycopg` изначально
> не был объявлен в зависимостях, и контейнер миграций упал бы при первом
> запуске. Нашлась она не тестом, а попыткой реально прогнать `alembic`.

### Шаг 2. Домен: объекты-значения

Начали с `TimeRange` — казалось бы, тривиальная пара чисел. Но:

```python
@dataclass(frozen=True, slots=True, order=True)
class TimeRange:
    start: float
    end: float
```

> **Зачем `frozen=True`**
>
> Отрезок времени, который можно поменять «на месте», расползётся по коду
> непредсказуемо: передали сцену в анализатор, он сдвинул границы «для себя» —
> и сдвинул их у всех, потому что объект один. Неизменяемость делает такую
> ошибку невозможной.
>
> Бонусом объект становится **хешируемым**: его можно положить в `set`
> и использовать ключом словаря. Изменяемый объект хешировать нельзя —
> иначе он «потеряется» в словаре после изменения.

> **Зачем `slots=True`**
>
> Убирает `__dict__` у экземпляра. Экономия — около 100 байт на объект
> и заметно более быстрый доступ к полям. На 2000 сцен × 40 признаков
> это уже мегабайты и миллионы обращений.

> **Почему полуинтервал `[start, end)`, а не отрезок `[start, end]`**
>
> Это не педантизм, а решение конкретной проблемы. Сцены идут подряд:
> `[0, 10)`, `[10, 20)`, `[20, 30)`. Если считать границу включённой,
> соседние сцены **пересекаются в точке 10** — и на Этапе 7 алгоритм NMS,
> отсеивающий пересекающиеся кандидаты, выбросит половину нормальных сцен.
>
> В коде это выражено так:
> ```python
> def overlaps(self, other):
>     return self.start < other.end - EPSILON and other.start < self.end - EPSILON
> ```
> И проверено тестом `test_touching_ranges_do_not_overlap`.

> **Что за `EPSILON = 1e-6` и почему нельзя сравнивать float напрямую**
>
> `0.1 + 0.2 == 0.3` в Python даёт `False` — это свойство двоичной
> плавающей точки, а не баг. Секунды видео складываются и вычитаются
> постоянно, поэтому все сравнения идут с допуском.
>
> Почему именно 1 мкс: кадр даже при 240 fps длится 4 мс, то есть в 4000 раз
> больше. Допуск заведомо меньше любой значимой для нас величины.

> **Зачем `iou()` в объекте-значении**
>
> Intersection over Union — метрика похожести отрезков от 0 до 1.
> Она понадобится на Этапе 7 в алгоритме NMS: «если новый кандидат
> перекрывается с уже выбранным более чем на 30 %, отбросить его».
> Метод живёт в домене, потому что это свойство отрезков, а не деталь
> алгоритма отбора.

### Шаг 3. `MediaWindow` — абстракция, ради которой всё затевалось

```python
@dataclass(frozen=True, slots=True)
class MediaWindow:
    source_id: str
    range: TimeRange
    index: int = 0
    is_final: bool = True
```

Четыре поля, и в них — вся будущая поддержка стримов.

> **Как это работает**
>
> Конвейер нигде не принимает «видеофайл». Он принимает пару
> `(LocalMedia, MediaWindow)` — «вот кусок медиа, вот его границы».
>
> | | Файл | Стрим (будущее) |
> |---|---|---|
> | Сколько окон | Одно, `[0, duration]` | Бесконечно, по 60–120 с |
> | `is_final` | `True` | `False` — за окном придут данные |
> | Кто их порождает | `LocalFileProvider.windows()` | `TwitchProvider.windows()` |
>
> Детектор сцен, все анализаторы, скоринг и LLM **не знают**, что перед ними.
> Поэтому добавление Twitch не потребует правок в конвейере — только новый
> класс, реализующий `SourceProvider`.
>
> **Альтернатива, которую мы отвергли:** сделать поддержку файлов сейчас,
> а стримы «прикрутить потом». На практике «потом» означает переписывание
> сигнатур всех анализаторов — а их к Этапу 5 будет двенадцать.
> Абстракция стоит четырёх полей сейчас и экономит неделю потом.

### Шаг 4. Порты

Девять протоколов. Разберу два самых показательных.

```python
class FeatureAnalyzer(Protocol):
    key: ClassVar[str]
    requires: ClassVar[frozenset[str]]
    produces: ClassVar[frozenset[str]]
    cost: ClassVar[int]

    async def analyze(self, context, scenes) -> Mapping[int, Sequence[FeatureValue]]: ...
```

> **Зачем четыре атрибута класса рядом с одним методом**
>
> Это не метаданные «для документации» — это вход планировщика.
> `requires`/`produces` строят граф зависимостей, `cost` определяет
> порядок внутри слоя, `key` позволяет включать и отключать анализатор.
>
> Без них планировщик пришлось бы кормить отдельным конфигом, который
> неизбежно разошёлся бы с кодом. Здесь объявление зависимости лежит
> **в том же файле**, что и её использование.

```python
class LLMProvider(Protocol):
    async def rank_scenes(self, scenes, context) -> Sequence[LLMVerdict]: ...
    async def generate_metadata(self, highlight, transcript, language) -> ClipMetadata: ...
```

> **Почему интерфейс узкий, а не «отправь произвольный промпт»**
>
> Соблазнительно объявить `async def complete(prompt: str) -> str` — гибко
> и универсально. Но тогда **промпты окажутся в вызывающем коде**, и подмена
> провайдера (другая модель, локальная LLM, заглушка в тестах) потребует
> переписывать их все.
>
> Узкий интерфейс объявляет **задачу**, а не способ. Промпт становится
> деталью реализации адаптера — там ему и место.

### Шаг 5. Реестр и планировщик

Ключевой момент реализации:

```python
while pending:
    ready = [cls for key, cls in pending.items() if set(cls.requires).issubset(satisfied)]
    if not ready:
        raise DependencyResolutionError(
            "Невозможно построить план анализа: зависимости неразрешимы",
            unresolved=sorted(pending),
            missing=sorted(_missing_requirements(pending.values(), satisfied)),
        )
    ready.sort(key=lambda cls: (-cls.cost, cls.key))
    layers.append(ready)
    for cls in ready:
        del pending[cls.key]
        satisfied |= set(cls.produces)
```

> **Почему в ошибку кладётся `missing` и `unresolved`**
>
> Сообщение «зависимости неразрешимы» само по себе бесполезно. С контекстом
> оно звучит так: «не удалось запланировать `audio.loudness`, не хватает
> `artifact.audio`» — и сразу понятно, что у видео нет звуковой дорожки.
>
> Правило: **ошибка должна содержать всё, что нужно для диагноза**, потому что
> в момент её чтения (три часа ночи, прод) отладчика под рукой не будет.

> **Почему `-cost` при сортировке**
>
> Минус даёт убывание: дорогие первыми. Логика такая: если в слое есть
> анализатор на 10 минут и три по минуте, и дорогой запустится последним,
> слой займёт 13 минут. Если первым — 10 минут, дешёвые успеют параллельно.

### Шаг 6. ORM и первая миграция

Восемь таблиц. Три момента, которые стоит отметить.

> **Почему `features` — это JSONB, а не таблица `scene_features`**
>
> Нормализованный вариант (`scene_id`, `key`, `value`) строже и «правильнее»
> с точки зрения теории. Но: 40 признаков × 2000 сцен = 80 000 строк
> **на одно видео**, и джойн на каждом обращении к сцене.
>
> Главный аргумент даже не в производительности: набор признаков **меняется
> с каждым новым плагином**. Сторонний анализатор из чужого пакета не может
> добавить колонку в нашу таблицу — а положить свой ключ в JSONB может.
>
> Строгость мы не теряем: структуру валидирует Pydantic на входе,
> а GIN-индекс по JSONB покрывает поиск по значению признака.

> **Что такое частичный индекс и зачем их три**
>
> ```sql
> CREATE UNIQUE INDEX uq_jobs_video_params ON jobs (video_id, params_hash)
>   WHERE status = 'succeeded';
> ```
> Уникальность применяется **только к строкам, удовлетворяющим условию**.
> Здесь это означает: «успешный джоб на данное видео с данными параметрами
> может быть только один». При этом неудачных попыток может быть сколько угодно.
>
> Именно этот индекс делает `POST /analyze` идемпотентным на уровне БД,
> а не на уровне «проверим сначала, потом вставим» — который ломается
> при двух одновременных запросах.

> **Почему `lazy="raise"` во всех связях**
>
> По умолчанию SQLAlchemy подгружает связанные объекты при обращении.
> В асинхронном коде это приводит к `MissingGreenlet` — падению в проде
> с непонятным сообщением. `lazy="raise"` превращает это в явную ошибку
> «ты не загрузил связь» ещё при разработке.

### Шаг 7. FastAPI

> **Почему `create_app()` — фабрика, а не модульный `app = FastAPI()`**
>
> Тесту нужно поднять приложение с подменёнными настройками, не трогая
> глобальное состояние. С модульным синглтоном пришлось бы патчить модуль;
> с фабрикой — просто вызвать её заново.
>
> Модульный `app = create_app()` внизу файла всё равно есть — его требует
> uvicorn (`uvicorn api.main:app`).

> **Почему `lifespan`, а не `@app.on_event("startup")`**
>
> `on_event` устарел. `lifespan` — контекстный менеджер, и это даёт
> гарантию, которой не было: код после `yield` выполнится даже если
> при старте произошла ошибка. Соединения будут закрыты, а не подвиснут.

### Шаг 8. Celery

> **Почему все задачи принимают только `job_id`**
>
> Соблазн — передать в задачу объект `Job` или список сцен. Но аргументы
> задачи **сериализуются в JSON и хранятся в Redis**. Список из 2000 сцен —
> это мегабайты в брокере, который для этого не предназначен.
>
> Правило: **брокер передаёт указатели, а не данные**. Задача получает `job_id`
> и читает состояние из БД. Заодно это делает задачи перезапускаемыми:
> состояние всегда актуальное, а не то, что было при постановке в очередь.

> **Зачем `worker_process_init`, а не инициализация при импорте**
>
> Celery с пулом `prefork` **форкает** процессы. Ресурс, созданный до форка,
> либо ломается (соединение с БД, которое теперь используют два процесса),
> либо дублируется в каждом (модель на GPU × 4 = VRAM кончилась).
>
> Сигнал `worker_process_init` срабатывает **после** форка, в каждом процессе
> отдельно. Это единственное правильное место для инициализации тяжёлых ресурсов.

> **Почему ретраятся только два типа ошибок**
>
> ```python
> autoretry_for = (TransientError, ExternalServiceError)
> ```
> Ретраить всё подряд вредно: задача, упавшая из-за битого файла, упадёт
> одинаково пять раз, заняв воркер на всё это время и отодвинув живые задачи.
>
> Повторяются только те ошибки, где повтор **имеет шанс сработать**:
> временный сбой (диск занят) и недоступность внешнего сервиса.
> Ошибка валидации не ретраится никогда — вход не изменится.
>
> `retry_jitter=True` добавляет случайный разброс: без него сто задач,
> упавших одновременно из-за недоступности LLM, пойдут на повтор
> в один и тот же момент и положат сервис второй раз.

### Шаг 9. Тесты

127 тестов. Разберу самые содержательные.

**Property-based тестирование** (`hypothesis`) — вместо перечисления примеров
проверяется **свойство** на сотнях сгенерированных входов:

```python
@given(seconds=st.floats(min_value=0, max_value=359999.9))
def test_roundtrip(self, seconds):
    assert parse_timecode(format_timecode(seconds)) == pytest.approx(seconds, abs=0.001)
```

> **Что это ловит, чего не ловят обычные тесты**
>
> Обычный тест проверяет `921.48 → "00:15:21.480" → 921.48`. Property-тест
> проверяет то же самое на 100 случайных значениях, включая граничные:
> 0, 359999.9, значения, дающие переполнение при округлении.
>
> Реальный баг, который такой тест поймал бы: `59.9996` при наивной реализации
> превращается в `"00:00:59.1000"` (округлили миллисекунды после разбора
> на части). У нас есть отдельный тест `test_rounding_does_not_produce_60_seconds`
> именно на этот случай — потому что округление сделано **до** разбора.

> **Ловушка hypothesis, на которую я наступил при написании этого этапа**
>
> Первая версия теста про пересечение отрезков генерировала два независимых
> отрезка на `[0, 1000]` и отбрасывала непересекающиеся через `assume()`.
> Hypothesis отверг тест с ошибкой «отфильтровано 50 из 56 входов» —
> и был прав: почти все примеры выбрасывались, тест почти ничего не проверял.
>
> Правильно — **строить второй отрезок со смещением от первого**, чтобы
> пересечение было частым случаем, а не редкой удачей. Это общий принцип:
> если приходится много фильтровать, значит, генератор выбран неверно.

**Тест архитектуры** — уже разобран в теории. Стоит отметить, что он
`parametrize`-ован по пакетам: добавив новый адаптер в `ADAPTER_PACKAGES`,
получаешь проверку автоматически.

**Тест, доказывающий расширяемость:**

```python
def test_adding_analyzer_requires_no_core_changes(self):
    third_party = make_analyzer("thirdparty.vibe", requires={ARTIFACT_TRANSCRIPT})
    registry.register_analyzer(third_party)
    plan = registry.build_plan(available_artifacts={ARTIFACT_TRANSCRIPT})
    assert any(cls is third_party for layer in plan for cls in layer)
```

> Фейковый анализатор в тесте **ничего не наследует** из `core`. Он попадает
> в план исполнения только за счёт структурного соответствия протоколу.
> Это и есть проверка требования «плагины без изменения ядра» — не на словах,
> а исполняемым кодом.

### Шаг 10. Docker

> **Почему два Dockerfile, а не один с аргументом**
>
> Образы отличаются существенно: воркеру нужен ffmpeg (+180 МБ) и рантайм
> OpenCV, API — не нужен. Один файл с `ARG ROLE` и ветвлениями читается хуже
> и всё равно собирает всё для всех.

> **Почему зависимости ставятся ДО копирования кода**
>
> ```dockerfile
> COPY pyproject.toml README.md ./
> RUN pip install ".[worker]"
> COPY src/ /app/src/          # ← код копируется последним
> ```
> Docker кеширует слои. Изменил строчку в коде — пересобирается только
> последний слой, секунды. Если скопировать код первым, любая правка
> инвалидирует слой с зависимостями, и `pip install` пойдёт заново — минуты.
>
> Это самая частая ошибка в Dockerfile новичков и самая дорогая по времени.

> **Почему модели не кладутся в образ**
>
> Whisper large-v3 весит ~3 ГБ. В образе это означает: 3 ГБ пушится в реестр
> при каждой сборке, 3 ГБ качается на каждый деплой. Модели качаются при первом
> старте в volume `models:/models` (`HF_HOME=/models`) и переживают
> пересоздание контейнера.

> **Почему `USER 10001`, а не root**
>
> Приложение принимает и парсит файлы из интернета. Парсеры медиаформатов
> исторически — источник уязвимостей. Непривилегированный пользователь
> ограничивает ущерб от успешного эксплойта.

> **Почему миграции — отдельный сервис, а не команда в entrypoint API**
>
> ```yaml
> migrate:
>   command: ["alembic", "upgrade", "head"]
>   restart: "no"
> api:
>   depends_on:
>     migrate: { condition: service_completed_successfully }
> ```
> Если миграции запускать в entrypoint API, то при трёх репликах три процесса
> начнут мигрировать одновременно. Alembic возьмёт блокировку, но двое упадут
> с ошибкой и уйдут в рестарт. Отдельный одноразовый контейнер решает это
> структурно.

> **Почему `pg_isready`, а не «порт открыт»**
>
> PostgreSQL начинает слушать порт **раньше**, чем готов принимать запросы.
> Healthcheck по порту пропустит зависимые сервисы слишком рано, и миграции
> упадут на гонке. `pg_isready` спрашивает саму БД.

> **`stop_grace_period: 120s` у воркера**
>
> При остановке Docker шлёт SIGTERM и через 10 секунд по умолчанию убивает
> процесс. Наша задача может идти минутами. Вместе с `acks_late` увеличенное
> время означает: либо воркер доделает задачу, либо она вернётся в очередь
> целой. Без этого — потерянная работа.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `ModuleNotFoundError: No module named 'core'` | `src` не в `PYTHONPATH` | Запускать через установленный пакет (`pip install -e .`) или задать `PYTHONPATH=src`. В Docker это делает `ENV PYTHONPATH=/app/src` |

| `ruff`: сотни `RUF001/RUF002` про «ambiguous cyrillic» | Правило рассчитано на англоязычный код, реагирует на русские комментарии | Уже отключено в `pyproject.toml` с обоснованием |

### Найденные и исправленные проблемы

За этап обнаружилось шесть реальных ошибок. Полезнее самих ошибок — понимание,
**чем именно** каждая была поймана, потому что это показывает, зачем нужен
каждый вид проверки.

| # | Ошибка | Чем поймана |
|---|---|---|
| 1 | `psycopg` не объявлен в зависимостях — контейнер миграций упал бы при первом старте | Попыткой реально запустить `alembic` |
| 2 | `supports()` объявлен методом экземпляра, а резолвер вызывает его на классе | Написанием теста `test_register_and_resolve` |
| 3 | Property-тест отбрасывал 90 % сгенерированных входов | Самим hypothesis |
| 4 | `redis` не входил в extra `api` — `/health/ready` рапортовал `degraded` | Запуском в Docker |
| 5 | `autodiscover_tasks` искал несуществующий модуль — воркер отвечал `NotRegistered` | Запуском в Docker |
| 6 | Healthcheck воркера искал ноду не под тем именем — контейнер вечно `unhealthy` | Запуском в Docker |

**Ни одна из ошибок 4–6 не была бы найдена без реального запуска стека.**
Разберём две последние подробнее — они поучительны.

> **Почему тесты не поймали `NotRegistered`**
>
> Тест выполнял задачу в eager-режиме и проходил. Но задача «регистрировалась»
> только потому, что **тестовый файл сам импортировал** `workers.tasks.system`.
> Воркер импортирует **только** `workers.app` — и модуля задач там не было.
>
> ```python
> celery_app.autodiscover_tasks(["workers.tasks"], force=True)   # ищет workers.tasks.tasks
> ```
> `autodiscover_tasks` ищет модуль с именем `tasks` **внутри** каждого
> указанного пакета. Передав `workers.tasks`, мы заставили его искать
> `workers.tasks.tasks`, которого нет. Ошибки при этом не было — просто
> ничего не нашлось.
>
> Исправление — явный список вместо магии:
> ```python
> TASK_MODULES = ["workers.tasks.system"]
> celery_app = Celery("highlight_generator", include=TASK_MODULES)
> ```
>
> И тест, который это ловит, — в **отдельном процессе**, импортирующем ровно
> то же, что импортирует воркер:
> ```python
> code = ("from workers.app import celery_app;"
>         "celery_app.loader.import_default_modules();"   # ← это делает воркер при старте
>         "...")
> subprocess.run([sys.executable, "-c", code], ...)
> ```
> Отдельный процесс здесь обязателен: в текущем модуль задач уже импортирован
> самим тестовым файлом, и проверка была бы бессмысленной.
>
> **Важная деталь**, найденная при написании этого теста: обращения к
> `celery_app.tasks` недостаточно — модули из `include` подтягиваются вызовом
> `loader.import_default_modules()`, который делает воркер при старте.
> Тест, забывший этот вызов, падал бы даже на исправном коде.

> **Как проверить, что тест вообще способен упасть**
>
> Тест, который не может провалиться, хуже отсутствующего: он даёт ложную
> уверенность. Проверка заняла одну команду:
> ```
> без include -> False      # задача не зарегистрирована
> с include   -> True       # зарегистрирована
> ```
> Возьмите за правило: написав тест на конкретный баг, **сломайте код обратно**
> и убедитесь, что тест краснеет.

> **Расхождение между entrypoint и healthcheck**
>
> ```bash
> # entrypoint.sh задавал имя ноды...
> --hostname="%h-${QUEUES//,/-}"          # → celery@f579-cpu-io
> # ...а healthcheck искал другое
> celery inspect ping -d "celery@$HOSTNAME"   # → celery@f579
> ```
> Воркер жив, задачи выполняет, но Docker считает контейнер `unhealthy` —
> и в проде оркестратор начал бы его перезапускать по кругу.
>
> Причина в дублировании: формула имени была записана в двух местах и разошлась.
> Исправление — одна формула, продублированная с явным комментарием
> «обязана совпадать с …»:
> ```bash
> NODE="${QUEUES%%,*}"          # "cpu" из "cpu,io"
> --hostname="${NODE}@%h"       # → cpu@f579690c08c5
> ```
> `${VAR%%,*}` вместо `${VAR//,/-}` выбрано не случайно: healthcheck выполняется
> в `/bin/sh` (dash), где bash-подстановка `//` не работает, а `%%` — стандарт POSIX.

**Общий вывод этапа.** Три уровня проверки поймали три разных класса ошибок:

| Уровень | Что ловит | Что пропускает |
|---|---|---|
| Юнит-тесты | Логику, граничные случаи | Всё, что связано со сборкой и запуском |
| `mypy` / `ruff` | Типы, несогласованность сигнатур | Ошибки конфигурации |
| **Реальный запуск** | Зависимости, discovery, healthcheck, права | Редкие ветки логики |

Отсюда правило проекта: **DoD этапа не закрывается, пока результат не запущен
по-настоящему**. «Тесты зелёные» — необходимое условие, но не достаточное.

две реализации `ObjectStorage` (локальная ФС и S3), проходящие один и тот же
набор тестов; первые сценарии в `core/usecases`; эндпоинты `POST /upload`
и чанковая загрузка больших файлов.

Там же станет видно, работает ли архитектура: если добавление источника
потребует правок в ядре — значит, границы прочерчены неверно, и лучше
узнать это на втором этапе, чем на восьмом.
