# Этап 2: Загрузка видео

## Цель этапа

Довести систему до состояния, когда видео **попадает внутрь и живёт там**:

1. Первый настоящий адаптер источника — `SourceProvider` для локальных файлов
   и для загруженных.
2. Чтение технических параметров через `ffprobe`.
3. Два хранилища за одним портом: локальная ФС и S3/MinIO.
4. Репозитории и Unit of Work поверх SQLAlchemy — первый выход домена в БД.
5. Сценарии: загрузить, зарегистрировать, показать, удалить.
6. HTTP: `POST /upload`, чанковая загрузка, `GET/DELETE /videos`.
7. Минимальная аутентификация — без неё «владелец видео» ничего не значит.

Главная проверка этапа не в тестах, а в вопросе: **потребовала ли правок
архитектура?** Если добавление источника заставило менять ядро — границы
прочерчены неверно, и лучше узнать это сейчас.

## Теория

### `SourceProvider`: почему это не «загрузчик файлов»

Порт называется не `FileLoader` и не `Downloader`, и это существенно.
Его задача — превратить **любой** источник в пару «файл на диске + окно времени»:

```
        ┌──────────────────┐
file:// │ LocalFileProvider│──┐
        └──────────────────┘  │
        ┌──────────────────┐  │      ┌─────────────┐     ┌──────────┐
upload://│ UploadProvider  │──┼─────▶│ LocalMedia  │────▶│ конвейер │
        └──────────────────┘  │      │ MediaWindow │     └──────────┘
        ┌──────────────────┐  │      └─────────────┘
youtube │ (Этап N)         │──┘
        └──────────────────┘
```

Четыре метода, и каждый решает свою задачу:

| Метод | Файл | Стрим (будущее) |
|---|---|---|
| `supports(uri)` | `uri.startswith("file://")` | `"twitch.tv" in uri` |
| `describe(uri)` | `ffprobe` | запрос к API платформы |
| `windows(uri)` | одно окно `[0, duration]` | бесконечный генератор окон |
| `acquire(uri, window)` | путь как есть | скачать сегмент во временный файл |
| `release(media)` | ничего | удалить сегмент |

> **Зачем флаг `owned` в `LocalMedia`**
>
> ```python
> @dataclass(frozen=True, slots=True)
> class LocalMedia:
>     path: Path
>     info: MediaInfo
>     source_uri: str
>     owned: bool = False    # ← «файл наш, можно удалять»
> ```
>
> Без него `release()` пришлось бы делать по-разному для разных источников,
> то есть вызывающий код должен был бы знать тип провайдера — ровно то,
> от чего мы уходим.
>
> С флагом контракт один: «отдай медиа обратно, провайдер сам разберётся».
> Файл пользователя (`owned=False`) останется, скачанный сегмент
> (`owned=True`) удалится.
>
> **Цена ошибки здесь высокая:** перепутать значения — значит либо удалить
> исходник пользователя, либо забить диск временными файлами.

> **`supports()` — почему `classmethod`**
>
> ```python
> @classmethod
> def supports(cls, uri: str) -> bool: ...
> ```
> Резолвер перебирает **классы** провайдеров и спрашивает «ты умеешь это?»
> **до** создания экземпляра. Создание может требовать API-ключей, сетевого
> клиента, соединения с хранилищем — платить за это ради проверки схемы URI
> бессмысленно.
>
> Эта деталь всплыла на Этапе 1 при написании теста реестра: метод был
> объявлен обычным, и `provider_cls.supports(uri)` не работал.

### Почему ffprobe, а не библиотека

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`ffprobe` подпроцессом** (наш выбор) | Уже есть в образе (часть ffmpeg, нужного для нарезки). Понимает всё, что понимает ffmpeg. Никаких C-биндингов | Накладные расходы на запуск процесса (~50 мс) |
| `PyAV` (биндинги к libav) | Быстрее, без процесса | Ломается при обновлении системных библиотек, тяжело собирать, ещё одна зависимость на 30 МБ |
| `pymediainfo` | Простой | Другая библиотека под капотом — то, что прочитал MediaInfo, ffmpeg может не открыть |

Решающий аргумент — третья строка: **валидировать нужно тем же инструментом,
которым потом обрабатывать.** Если MediaInfo файл прочитал, а ffmpeg не смог,
мы примем файл и упадём на Этапе 8, далеко от причины.

> **Почему аргументы передаются списком, а не строкой**
>
> ```python
> args = [self._binary, "-v", "error", "-print_format", "json", ..., str(path)]
> await asyncio.create_subprocess_exec(*args)
> ```
> При строке и `shell=True` имя файла вида `movie.mp4; rm -rf /` было бы
> исполнено оболочкой. Список аргументов исключает интерпретацию оболочкой
> **в принципе** — не «экранирует», а делает невозможной.
>
> Имя файла у нас приходит от пользователя, так что это не паранойя.

### Расширение файла ничего не доказывает

Центральный принцип этапа. Переименованный `.txt` → `.mp4` пройдёт любую
проверку по имени. Отличить может только попытка прочитать содержимое.

Отсюда порядок из двух проверок:

```
1. Проверка имени  (дешёвая)  → отказать до приёма 20 ГБ
2. Приём файла на диск
3. Проверка содержимого через ffprobe (дорогая) → окончательный вердикт
```

Первая экономит трафик и место, вторая даёт истину. Обе нужны.

> **Тонкость: `.mp4` и `.mov` — это один формат**
>
> ffprobe для обоих отдаёт `format_name = "mov,mp4,m4a,3gp,3g2,mj2"`.
> Это семейство ISO BMFF, и различить `.mp4` от `.mov` по содержимому нельзя.
>
> Наивная проверка «расширение из белого списка == container из ffprobe»
> отвергла бы честный `.mov`. Поэтому сравниваются **семейства**:
>
> ```python
> CONTAINER_FAMILIES = {"mp4": "mp4", "mov": "mp4", "mkv": "mkv", "webm": "mkv"}
> ```

> **Тонкость: обложка альбома выглядит как видеопоток**
>
> У mp3 с картинкой ffprobe покажет видеопоток 1920×1080 из одного кадра.
> Без фильтра такой файл был бы принят за видео, и конвейер стал бы искать
> в нём сцены.
>
> ```python
> if kind == "video" and stream.get("disposition", {}).get("attached_pic"):
>     continue
> ```

### Один порт — два хранилища

`ObjectStorage` закрывает и локальную ФС, и S3. Разница не косметическая:

| | `LocalStorage` | `S3Storage` |
|---|---|---|
| Общий диск воркеров и API | **Обязателен** | Не нужен |
| Масштабирование воркеров по машинам | Невозможно | Свободно |
| Отдача файла клиенту | Через наш процесс | Presigned-ссылка, байты мимо нас |
| Настройка | Ноль | Бакет, ключи, endpoint |

Именно поэтому локальное хранилище — для разработки, S3 — для прода.
И именно поэтому **оба проходят один и тот же набор тестов**: если поведение
разойдётся, вызывающий код начнёт зависеть от того, какое хранилище настроено.

> **Почему `signed_url()` возвращает `None`, а не бросает исключение**
>
> У локальной ФС прямых ссылок не бывает. Вариант «бросать `NotImplementedError`»
> заставил бы роутер знать тип хранилища:
> ```python
> if isinstance(storage, S3Storage):   # ← так делать нельзя
> ```
> Вариант с `None` оставляет роутер честно неведающим:
> ```python
> signed = await storage.signed_url(key)
> if signed is not None:
>     return RedirectResponse(signed)      # S3: клиент идёт прямо в хранилище
> return StreamingResponse(storage.open_stream(key))   # локально: отдаём сами
> ```

> **Почему запись в локальное хранилище идёт через временный файл**
>
> ```python
> tmp = target.with_suffix(target.suffix + ".partial")
> shutil.copyfile(source, tmp)
> tmp.replace(target)          # ← атомарно в пределах одной ФС
> ```
> Прямая запись в `target` означает, что параллельный читатель может увидеть
> наполовину записанный файл. `rename` в пределах файловой системы атомарен:
> объект либо старый, либо новый, промежуточного состояния не существует.

> **Почему boto3 в пуле потоков, а не асинхронный клиент**
>
> Асинхронные обёртки (`aioboto3`, `aiobotocore`) существуют, но тянут
> собственный форк botocore и отстают от него по версиям. Наши обращения
> к хранилищу — единицы в секунду и почти всегда крупные файлы, где время
> уходит на сеть, а не на переключение задач.
>
> `asyncio.to_thread` даёт ту же неблокирующесть при одной зависимости
> вместо трёх. Если профилирование покажет, что пул потоков стал узким
> местом, замена затронет один файл — интерфейс не изменится.

### Repository и Unit of Work

**Repository** прячет способ хранения. Сценарий говорит «дай видео по
контрольной сумме», а не «сделай SELECT».

**Unit of Work** объединяет операции в транзакцию. Загрузка видео — как раз
такой случай: запись в `videos` и запись в `assets` должны появиться вместе,
иначе в базе окажется видео без файла или файл без владельца.

```python
async with uow_factory() as uow:
    stored = await uow.videos.add(video)
    await storage.put(key, upload.path)
    await uow.assets.add(...)
    await uow.commit()
```

> **Почему `__aexit__` делает `rollback`, а не `commit`**
>
> Забытый `commit()` даёт **отсутствие записи** — заметно сразу и находится
> за минуту. Забытый `rollback()` при обратном умолчании дал бы **частично
> применённую транзакцию** — эту ошибку в проде не поймать.
>
> Умолчание выбирается по цене ошибки, а не по удобству.

> **Почему `get_owned(video_id, user_id)`, а не `get(video_id)` + проверка**
>
> ```python
> stmt = select(VideoORM).where(
>     VideoORM.id == video_id,
>     VideoORM.user_id == user_id,          # ← проверка внутри запроса
>     VideoORM.status != VideoStatus.DELETED,
> )
> ```
> Если бы существовал только `get()`, рано или поздно в одном из десяти
> вызовов забыли бы сверить `video.user_id`, и появился бы доступ к чужим
> данным. Здесь забыть невозможно: другого способа получить видео нет.
>
> Это общий приём — **делать безопасный путь единственным**, а не самым
> удобным.

> **404 вместо 403 на чужой ресурс**
>
> Ответ 403 сообщает: «объект существует, но не ваш». Это подтверждение
> существования постороннему — по нему можно перебором выяснить, какие
> идентификаторы заняты.
>
> 404 не раскрывает ничего: чужое неотличимо от несуществующего.

### Возобновляемая загрузка: зачем и как

Обычный multipart на 20 ГБ плох по трём причинам: обрыв на 95 % означает
начать сначала; прокси режут длинные запросы по таймауту; прогресса не видно.

```
POST /upload/init                      → upload_id, chunk_size
PUT  /upload/{id}/part/1  (32 МиБ)     ┐
PUT  /upload/{id}/part/2  (32 МиБ)     ├ можно параллельно и не по порядку
PUT  /upload/{id}/part/3  (32 МиБ)     ┘
GET  /upload/{id}                      → чего не хватает после обрыва
POST /upload/{id}/complete             → сборка + обычный сценарий загрузки
```

> **Почему массив номеров частей, а не счётчик**
>
> ```sql
> received_parts INTEGER[] NOT NULL DEFAULT '{}'
> ```
> Части приходят **не по порядку** (параллельная отправка) и **повторно**
> (ретрай после таймаута). Счётчик на такое не отвечает на главный вопрос
> клиента: «чего именно не хватает?».
>
> Массив отвечает, и он же даёт идемпотентность: повторная отправка части 3
> не увеличивает счётчик байтов, потому что 3 уже в множестве.

> **Почему состояние в БД, а не в Redis**
>
> Redis с TTL напрашивается для короткоживущего состояния. Но здесь состояние
> связано с **файлами в хранилище**: потерять его — значит оставить мусор,
> который никто не удалит. Плюс загрузка 20 ГБ идёт минутами и должна
> пережить перезапуск API и переезд клиента на другую реплику.

> **Почему `complete` вызывает обычный `UploadVideo`, а не дублирует логику**
>
> ```python
> assembled = await self._assemble(upload_id, session)
> video, duplicate = await self._upload_video.execute(...)
> ```
> Иначе появились бы **два пути** появления видео в системе с расходящимся
> поведением: проверка формата, дедупликация, запись артефакта. Однажды
> один из них забыли бы обновить.
>
> Сборка — это подготовка файла; всё остальное делает существующий сценарий.

> **Почему дыра в нумерации — отказ, а не «соберём что есть»**
>
> Собрать без части технически можно. Получится видео, которое сломается
> на этапе анализа — далеко от места настоящей причины, с непонятной
> диагностикой. Честный 409 сейчас дешевле.

### Один проход по данным

```python
async for chunk in chunks:
    size += len(chunk)
    if size > max_bytes:
        raise ValidationError(...)  # обрываем в момент превышения
    digest.update(chunk)  # считаем SHA-256
    handle.write(chunk)  # пишем на диск
```

Три вещи за один проход, и каждая по своей причине:

- **Запись на диск** — держать 20 ГБ в памяти невозможно.
- **Хеш** — второй проход по 20 ГБ ради контрольной суммы это лишние минуты
  дискового чтения.
- **Лимит** — проверка обрывает приём **в момент** превышения, а не после
  того, как файл целиком занял место.

> **Почему нельзя доверять `Content-Length`**
>
> Заголовок присылает клиент. Он может соврать — заявить 1 МБ и слать
> бесконечный поток. Проверка по факту принятых байтов не обманывается.

> **Почему недописанный файл удаляется в `except BaseException`**
>
> ```python
> except BaseException:
>     destination.unlink(missing_ok=True)
>     raise
> ```
> Именно `BaseException`, а не `Exception`: обрыв соединения в ASGI приходит
> как `asyncio.CancelledError`, который от `Exception` **не наследуется**.
> С `except Exception` оборванные загрузки молча съедали бы диск.

### Минимальная аутентификация — почему не отложили

Полноценная авторизация запланирована на Этап 10. Но у видео есть владелец,
проверка владения — пункт DoD этого этапа, а «временный хардкод `user_id`»
имеет свойство доживать до продакшена.

> **Почему API-ключ хешируется SHA-256 без соли**
>
> Выглядит как ошибка — пароли так хешировать нельзя. Но ключ это не пароль:
>
> | | Пароль | API-ключ |
> |---|---|---|
> | Энтропия | Низкая, осмысленный | 256 бит случайности |
> | Атака | Перебор по словарю | Перебор невозможен |
> | Нужен медленный хеш | **Да** (argon2, bcrypt) | Нет |
> | Частота проверки | Раз за сессию | **Каждый запрос** |
>
> Соль защищает от радужных таблиц, которые для 256-битной случайности
> построить нельзя. А медленный хеш на каждом запросе — это медленный API.
>
> Для паролей пользователей на Этапе 10 будет argon2 — там ситуация обратная.

## Пошаговый разбор

### Шаг 1. Валидация переехала в домен

Изначально `validate_media` жила в `video_loader/validation.py`. Оказалось —
неверное место.

> **Почему это доменная политика, а не деталь загрузчика**
>
> «Какие контейнеры мы принимаем» — решение о продукте, одинаковое для
> загрузки через HTTP, регистрации локального файла и будущего импорта
> из YouTube. Три места использования, ноль зависимостей — это домен.
>
> Практическая причина острее: `core/usecases` **не имеет права** импортировать
> `video_loader` (адаптер). Пока валидация лежала там, сценарий её импортировал
> и нарушал правило зависимостей.
>
> Файл `video_loader/validation.py` остался реэкспортом — чтобы не ломать
> привычное место импорта.

### Шаг 2. Сценарии зависят только от портов

Первая версия `RegisterLocalVideo` конструировала провайдер сама:

```python
# было — работало, но неправильно
provider = LocalFileProvider(self._probe, self._allowed_roots)
```

```python
# стало — провайдер приходит снаружи
def __init__(self, *, uow_factory, provider: SourceProvider, limits): ...
```

> **Почему это важно, если результат одинаковый**
>
> В первом варианте заменить провайдер без правки сценария нельзя.
> То есть сценарий знает конкретную реализацию — и вся конструкция
> с портами перестаёт работать ровно там, где должна была помочь.
>
> Нарушение поймал не глаз, а **новый тест архитектуры**, который я добавил
> на этом этапе: `test_usecases_depend_only_on_domain_and_ports`.

### Шаг 3. Композиционный корень получил исключение в тесте

Тест архитектуры немедленно упал на `core/container.py`:

```
core/container.py → video_loader.providers.local
core/container.py → video_loader.probe
```

Формально — нарушение. По сути — нет: **композиционный корень обязан знать
реализации**, это его единственная работа.

> **Как правильно оформить исключение из правила**
>
> Не «отключить проверку», а сузить её и добавить обратную:
>
> ```python
> COMPOSITION_ROOT = "core/container.py"
>
> def test_core_does_not_import_adapters_outside_composition_root(): ...
> def test_composition_root_is_the_only_place_wiring_adapters(): ...
> ```
>
> Второй тест нужен, потому что первый можно «пройти», перестав связывать
> что-либо вовсе. Он следит, чтобы исключение оставалось осмысленным:
> если импорты адаптеров из корня исчезли — значит, связывание уехало
> куда-то ещё, и надо разобраться куда.

### Шаг 4. Мост «video_id → storage_key»

`UploadProvider` нужен ключ в хранилище, а в URI лежит только `video_id`.
Связь знает БД — но провайдер не должен зависеть от репозиториев.

```python
type KeyResolver = Callable[[UUID], Awaitable[str]]


class UploadProvider:
    def __init__(self, storage, probe, *, key_resolver: KeyResolver | None = None): ...
```

Контейнер подставляет функцию, читающую БД; тест подставляет словарь.

> **Первая версия вычисляла ключ сама — и была неверна**
>
> ```python
> return f"{video_prefix(video_id)}/source"     # ← а в хранилище source.mkv
> ```
> Ключ включает расширение исходника, а его в URI нет. Ошибка нашлась
> при перечитывании кода, до запуска, — но именно потому, что докстринг
> обещал одно, а код делал другое. Расхождение докстринга и кода —
> хороший индикатор.

### Шаг 5. Порядок операций в сценарии загрузки

```
1. ffprobe            ← проверка содержимого
2. validate_media     ← проверка правил
3. get_by_checksum    ← дедупликация
4. videos.add         ← запись в БД
5. storage.put        ← запись файла
6. assets.add         ← учёт артефакта
7. commit
```

> **Почему проверка раньше записи в хранилище**
>
> Иначе мы платим за место под файлы, которые сами же и отвергаем,
> и потом их чистим. Отдельный тест это фиксирует:
> `test_nothing_is_stored_when_validation_fails`.

> **Почему `storage.put` внутри транзакции, а не после коммита**
>
> Разберём оба порядка по худшему случаю:
>
> | Порядок | Что будет при сбое |
> |---|---|
> | put → commit (наш) | Транзакция откатилась → **осиротевший файл**. Подберёт уборка |
> | commit → put | Файл не записался → **запись без файла**. Пользователь не выберется |
>
> Осиротевший файл — исправимая неприятность, запись без файла — тупик.
> Выбираем по цене худшего случая.

> **А почему при удалении порядок обратный?**
>
> ```python
> await uow.commit()          # сначала фиксируем
> await self._delete_files()  # потом удаляем файлы
> ```
> Та же логика, зеркально: если удалить файлы первыми и транзакция
> откатится, останется живая запись без файлов. Худший случай при нашем
> порядке — снова осиротевшие файлы.
>
> Общее правило: **необратимую операцию (удаление байтов) делаем последней.**

### Шаг 6. Мягкое удаление записи, настоящее удаление файлов

```python
await uow.videos.mark_deleted(video_id)  # статус deleted, строка остаётся
await self._delete_files(video)  # байты удаляются по-настоящему
```

> **Почему по-разному**
>
> На запись ссылаются джобы, сцены, клипы; история обработки нужна для
> разбора инцидентов. А вот файлы занимают место **реально**, и хранить
> 20 ГБ ради истории незачем.

> **Почему сбой уборки не ломает удаление**
>
> ```python
> except Exception as error:
>     log.warning("video.file_cleanup_failed", ...)
> ```
> Запись уже помечена удалённой; для пользователя операция состоялась.
> Ронять запрос из-за недоступного S3 — значит оставить его в состоянии
> «не удалилось», хотя фактически удалилось.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `415` на нормальный `.mov` | Сравнение расширений вместо семейств контейнеров | ffprobe для mp4 и mov отдаёт одно `format_name`; сравнивать через `CONTAINER_FAMILIES` |
| mp3 с обложкой принят за видео | Обложка лежит как видеопоток из одного кадра | Фильтровать потоки с `disposition.attached_pic` |
| Длительность `0` у корректного mkv | В заголовке контейнера её нет | Брать максимум из длительностей дорожек |
| `403 SignatureDoesNotMatch` на presigned-ссылке | Ссылка подписана для внутреннего хоста | Задать `S3_PUBLIC_ENDPOINT_URL`; хост входит в подпись SigV4 |
| `can't subtract offset-naive and offset-aware datetimes` | Колонка `TIMESTAMP` вместо `TIMESTAMPTZ` | Все колонки времени — `DateTime(timezone=True)` |
| Диск заполняется при обрывах загрузки | Недописанный файл не удаляется | `except BaseException` — `CancelledError` не наследует `Exception` |
| `413` вместо `415` на большом не-видео | Лимит проверяется раньше формата | Так и задумано: дешёвая проверка первой |
| Загрузка проходит, но файла в хранилище нет | `put` после `commit`, сбой между ними | Класть файл внутри транзакции |
| Чужое видео отдаёт `403` | Раскрытие существования объекта | Отдавать `404`; проверка владения — в SQL-запросе |
| `MinIO недоступен` при запуске тестов | Профиль `s3` не поднят | `docker compose --profile s3 up -d minio` |
| Тесты БД массово пропускаются | PostgreSQL не запущен или порт не проброшен | `docker compose up -d postgres`; проверить `docker compose ps` |
| Миграции не применяются после правки | Образ `migrate` не пересобран | У него отдельный образ: `docker compose build` без аргументов |

### Найденные и исправленные проблемы

Восемь дефектов за этап. Как и на Этапе 1, интереснее не они сами,
а **чем именно** каждый был пойман.

| # | Дефект | Чем пойман |
|---|---|---|
| 1 | Сценарий импортировал адаптер напрямую | Новым тестом архитектуры |
| 2 | `UploadProvider` вычислял ключ без расширения | Расхождением докстринга и кода при перечитывании |
| 3 | `postgres`/`redis` без политики перезапуска | Тесты БД массово ушли в skip после перезапуска Docker |
| 4 | Колонки времени как `TIMESTAMP` вместо `TIMESTAMPTZ` | Первым же запуском чанковой загрузки на живой БД |
| 5 | Изменяемые атрибуты в `Protocol` инвариантны | `mypy --strict` |
| 6 | Переименованный `.txt` давал 400 вместо 415 | Сквозной проверкой на живом стеке |
| 7 | В тексте ошибки утекал внутренний путь сервера | Той же сквозной проверкой |
| 8 | Presigned-ссылка подписана для внутреннего хоста | Сквозной проверкой пути S3 |

Три из восьми разберём подробно.

> **Дефект 4: `TIMESTAMP` против `TIMESTAMPTZ`**
>
> ```
> asyncpg.exceptions.DataError: invalid input for query argument $9:
> datetime.datetime(2026, 8, 3, ...) (can't subtract offset-naive and offset-aware)
> ```
> Это не «косметика». `TIMESTAMP WITHOUT TIME ZONE` хранит момент времени
> **без указания, в каком поясе он записан**. Два процесса в разных поясах
> запишут в одну колонку разные моменты, и отличить их потом невозможно.
> Для системы, где воркеры могут стоять на других машинах, это гарантированная
> порча данных.
>
> Исправление — миграция `0003` с `USING ... AT TIME ZONE 'UTC'`: уже
> записанные значения трактуются как UTC, что верно, потому что всё писалось
> в UTC.
>
> Заметьте: **миграцию 0001 править нельзя** — она уже применена. Правильный
> путь всегда «новая миграция», даже когда исходная содержала ошибку.

> **Дефект 5: почему `Protocol` не принял подтип**
>
> ```
> assets: expected "AssetRepositoryPort", got "AssetRepository"
> ```
> `AssetRepository` полностью реализует протокол. Но объявление в `Protocol`
> было **изменяемым атрибутом**:
> ```python
> class UnitOfWork(Protocol):
>     assets: AssetRepositoryPort        # ← инвариантно
> ```
> Изменяемый атрибут можно и читать, и писать. Если бы подтип подходил,
> кто-то мог бы записать в это поле другой объект того же протокола —
> и статическая гарантия сломалась бы. Поэтому mypy требует **точного**
> совпадения типа.
>
> Решение — объявить свойство, доступное только для чтения:
> ```python
>     @property
>     def assets(self) -> AssetRepositoryPort: ...
> ```
> Читать можно, писать нельзя → ковариантно → подтип подходит.
> Обычный атрибут в реализации свойству протокола соответствует.
>
> Это общее правило Python-протоколов, и оно неочевидно ровно до первой
> встречи с ним.

> **Дефект 8: presigned-ссылка и SigV4**
>
> ```
> Location: http://minio:9000/highlights/videos/.../source.mp4?X-Amz-Signature=...
> → 403 SignatureDoesNotMatch
> ```
> Хост **входит в подпись** SigV4. Сервер ходит в хранилище по внутреннему
> адресу (`http://minio:9000`), а браузер пользователя — по внешнему.
> Ссылка, подписанная для внутреннего хоста, при обращении по внешнему
> отвергается. Подменить хост в готовой ссылке нельзя — подпись развалится.
>
> Решение — второй клиент boto3, привязанный к публичному адресу и
> используемый **только для подписи**:
> ```python
> self._signing_client = (
>     make_client(public_endpoint_url)
>     if public_endpoint_url and public_endpoint_url != endpoint_url
>     else self._client
> )
> ```
>
> Показательно, что 29 тестов хранилища этого не ловили: они проверяли
> контракт «ссылка или `None`», а не то, **для какого хоста** она подписана.
> После исправления добавлены два теста, которые ловят.

**Вывод этапа.** Три дефекта из восьми (6, 7, 8) нашла только сквозная
проверка на живом стеке, и все три — в поведении, которое юнит-тесты
считали корректным, потому что фейк вёл себя иначе, чем настоящий ffprobe
и настоящий S3.

Это не аргумент против фейков — без них 250 тестов не проходили бы за
20 секунд. Это аргумент за то, что **фейк проверяет логику, а живой прогон
проверяет предположения о внешнем мире.** Нужны оба.
