# 06 — LLM-слой

## 6.1 Роль LLM в системе

LLM решает две задачи, которые не решаются сигналами:

1. **Понимание смысла.** Сигналы видят «громко + быстрый монтаж». Модель по транскрипту
   понимает, что здесь герой раскрывает тайну — это и есть «неожиданный поворот».
2. **Генерация метаданных.** Заголовок, описание, хештеги для готового клипа.

LLM **не** заменяет эвристику: она работает поверх уже посчитанных сигналов
и получает компактную сводку сцены, а не сырое видео. Это на порядки дешевле
и делает систему работоспособной при отключённой LLM (док 05, §5.6).

## 6.2 Выбор модели

| Задача | Модель | Обоснование |
|---|---|---|
| Ранжирование сцен | `claude-opus-5` | Смысловая оценка «интересности» — задача на суждение, качество окупается |
| Генерация метаданных | `claude-opus-5` | Тот же клиент, тот же кеш; объём выхода мал |

Цена `claude-opus-5`: **$5 / 1M входных, $25 / 1M выходных токенов**.
Контекст 1M токенов, максимум 128K выходных.

Модель настраивается через `LLM_MODEL` — порт `LLMProvider` позволяет подменить
провайдера целиком (например, на локальную модель) без правки конвейера.

> **Важно про thinking.** На `claude-opus-5` расширенное мышление включено по умолчанию:
> запрос без параметра `thinking` всё равно думает, и `max_tokens` ограничивает
> **сумму** «мышления» и ответа. Поэтому `max_tokens` для ранжирования ставим
> с запасом (≥ 8000 на батч из 40 сцен) и управляем глубиной через
> `output_config.effort`, а не через устаревший `budget_tokens` (он вернёт 400).

## 6.3 Контракт: строгий JSON

Формат из ТЗ:

```json
[
  {
    "start": "00:15:21",
    "end":   "00:16:05",
    "score": 96,
    "category": "action",
    "reason": "Интенсивная сцена погони."
  }
]
```

> ⚠️ В исходном ТЗ тайм-коды записаны без кавычек (`"start": 00:15:21`) — это
> невалидный JSON, такой документ не разберёт ни один парсер. Мы используем
> строки `"HH:MM:SS"` (с опциональными миллисекундами `HH:MM:SS.mmm`)
> и конвертируем их в секунды на границе слоя. Внешний контракт API отдаёт
> **и** строку, и число секунд — см. док 07.

Формат гарантируется не «просьбой в промпте», а параметром `output_config.format`
со строгой JSON-схемой — модель физически не может вернуть другую структуру.

```python
class SceneVerdict(BaseModel):
    scene_index: int = Field(ge=0)  # привязка к нашей сцене — ключ надёжности
    start: str = Field(pattern=r"^\d{2}:\d{2}:\d{2}(\.\d{1,3})?$")
    end: str = Field(pattern=r"^\d{2}:\d{2}:\d{2}(\.\d{1,3})?$")
    score: int = Field(ge=0, le=100)
    category: Literal[
        "action",
        "funny",
        "emotional",
        "plot_twist",
        "dialogue",
        "tension",
        "romantic",
        "informative",
        "other",
    ]
    reason: str = Field(max_length=300)


class RankingResponse(BaseModel):
    verdicts: list[SceneVerdict]
```

`scene_index` — обязательное поле, которого нет в ТЗ, но без него нельзя надёжно
сопоставить вердикт с нашей сценой: модель может слегка сместить тайм-коды.
Сопоставляем по индексу, а тайм-коды из ответа используем как подсказку
для уточнения границ (и валидируем, что они лежат внутри сцены ± 2 с).

Вызов:

```python
response = await client.messages.parse(
    model="claude-opus-5",
    max_tokens=8000,
    system=[
        {
            "type": "text",
            "text": RANKING_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"},
        },  # ← точка кеширования 1
        {
            "type": "text",
            "text": video_context_block,
            "cache_control": {"type": "ephemeral"},
        },  # ← точка кеширования 2
    ],
    output_config={"format": RankingResponse, "effort": "high"},
    messages=[{"role": "user", "content": scenes_batch_block}],  # ← меняется каждый батч
)
verdicts = response.parsed_output.verdicts
```

## 6.4 Что именно уходит в модель

Не транскрипт целиком и не сырые признаки. На каждую сцену — компактный блок:

```
### Сцена 47 | 00:15:21 – 00:16:05 (44.0 с)
Сигналы: action 0.91, tension 0.62, emotional_speech 0.34, laughter 0.02
Аудио: громкость +8.2 дБ к медиане, пауз 4%, темп речи 178 wpm (+34%)
Видео: склеек 12 (0.27/с), движение 0.84, лиц max 3, крупный план нет
Речь: «Держись! Они прямо за нами — сворачивай направо, быстро!»
Контекст: предыдущая сцена — спокойный диалог; следующая — тишина 6 с
```

Правила формирования (в `llm/summarizer.py`):

- Речь обрезается до 600 символов: начало + `…` + конец, если длиннее.
- Признаки округляются до 2 знаков — лишняя точность тратит токены впустую.
- Сцены без речи и с низким скором по всем сигналам (< 0.15) в LLM **не отправляются** —
  они заведомо не хайлайты. Экономия обычно 40–60 % батча.
- Контекст соседей нужен, чтобы модель видела контраст — главный маркер поворота.

## 6.5 Кеширование промптов

Кеш работает по **префиксу**: любое изменение байта инвалидирует всё после него.
Отсюда порядок блоков — от самого стабильного к самому изменчивому:

```
[system: инструкция ранжирования]     ← одинакова для всех видео и всех джобов
[system: контекст видео]              ← одинаков для всех батчей этого видео
[user:   батч сцен]                   ← меняется, вне кеша
```

- Чтение из кеша ≈ 0.1× цены, запись ≈ 1.25×. Уже со второго батча — экономия.
- Минимальный кешируемый префикс на `claude-opus-5` — **512 токенов**
  (на Opus 4.8 было 1024), поэтому даже наша инструкция помещается в кеш.
- В системном промпте **не должно быть** ни текущей даты, ни `job_id`, ни UUID —
  это классический «тихий инвалидатор», обнуляющий кеш на каждом запросе.
- Проверка в интеграционном тесте: со второго запроса `usage.cache_read_input_tokens > 0`.

## 6.6 Batch API для массового ранжирования

Двухчасовое видео → ~1200 сцен → после фильтра ~500 → ~13 батчей по 40 сцен.
Латентность здесь не важна (джоб и так идёт минуты), поэтому используем
**Message Batches API: −50 % к цене**.

```python
batch = await client.messages.batches.create(
    requests=[
        Request(
            custom_id=f"job-{job_id}-batch-{i}",
            params=MessageCreateParamsNonStreaming(
                model="claude-opus-5",
                max_tokens=8000,
                system=cached_system_blocks,
                output_config={"format": RankingResponse, "effort": "high"},
                messages=[{"role": "user", "content": block}],
            ),
        )
        for i, block in enumerate(batches)
    ]
)
```

- Джоб не блокируется: `llm_rank` создаёт батч, сохраняет `batch_id` в `jobs.stage_states`
  и завершается. Beat-задача `poll_llm_batches` (док 04, §4.9) забирает результаты
  и запускает продолжение цепочки.
- Результаты приходят **в произвольном порядке** — сопоставляем строго по `custom_id`,
  никогда по позиции.
- Батчи обычно готовы за минуты, гарантия — 24 ч. Если `params.llm_sync = true`
  (интерактивный режим), используется обычный синхронный путь без скидки.
- Fallback: при `expired` / `errored` для конкретного `custom_id` — повторить
  синхронно только этот батч, не весь набор.

## 6.7 Обработка отказов модели

`claude-opus-5` может вернуть **HTTP 200** со `stop_reason: "refusal"` — сработали
классификаторы безопасности (актуально для контента с насилием, что для фильмов
не экзотика). Код, который читает `response.content[0]` без проверки, здесь сломается.

```python
if response.stop_reason == "refusal":
    log.warning("llm_refusal", category=getattr(response.stop_details, "category", None))
    return []  # сцены остаются с одной лишь эвристикой, джоб → partial
```

Дополнительно включаем серверный фоллбек — отказ будет автоматически переигран
на другой модели внутри того же вызова:

```python
response = await client.beta.messages.create(
    model="claude-opus-5",
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",        # маршрутизация по категории отказа
    ...
)
```

## 6.8 Генерация метаданных клипа

Отдельный вызов на каждый отобранный клип, со своей схемой:

```python
class ClipMetadata(BaseModel):
    title: str = Field(max_length=100)
    description: str = Field(max_length=500)
    hashtags: list[str] = Field(min_length=3, max_length=10)
    hook: str = Field(max_length=120)  # первая фраза для превью/обложки
```

Вход: транскрипт клипа, категория, `reason` из ранжирования, язык видео.
Промпт задаёт язык вывода = язык исходной речи и запрещает кликбейт-штампы.

Эти вызовы дёшевы (короткий вход и выход) и идут синхронно, параллельно по клипам,
в очереди `net` с ограничением конкурентности.

## 6.9 Оценка стоимости

Двухчасовой фильм, 500 сцен после фильтра, батчи по 40:

| Статья | Токенов | Цена |
|---|---|---|
| Системный промпт (кеш, запись 1×) | ~1 200 | $0.0075 |
| Системный промпт (кеш, чтение ×12) | ~14 400 | $0.0072 |
| Сцены (вход, ~180 ток./сцена) | ~90 000 | $0.45 |
| Вердикты (выход, ~60 ток./сцена) | ~30 000 | $0.75 |
| Метаданные 10 клипов | ~8 000 | $0.10 |
| **Итого синхронно** | | **≈ $1.31** |
| **Итого через Batch API (−50 %)** | | **≈ $0.66** |

Дальнейшее снижение до целевых $0.30/час (док 01, §1.7): агрессивнее фильтровать
сцены перед LLM (порог 0.25 вместо 0.15) и сокращать `reason` до 150 символов.
Замер фактической стоимости пишется в `jobs.cost` на каждом джобе.

## 6.10 Устойчивость

| Риск | Меры |
|---|---|
| Rate limit (429) | SDK ретраит сам; поверх — семафор на очередь `net` и backoff |
| Таймаут / обрыв | `max_retries=5`, экспоненциальный backoff с джиттером |
| Невалидный JSON | Невозможен при `output_config.format`; на всякий случай — Pydantic-валидация + один ретрай с уточнением |
| Модель «поплыла» по индексам | Валидация: `scene_index` существует, тайм-коды внутри сцены ± 2 с; иначе вердикт отбрасывается |
| API недоступен полностью | Circuit breaker → джоб идёт по эвристике, статус `partial` |
| Смена версии модели | `LLM_MODEL` в конфиге + фиксация в `jobs.params`, чтобы результаты были воспроизводимы |

## 6.11 Тестирование LLM-слоя

- **Unit.** `FakeLLMProvider` возвращает детерминированные вердикты — весь конвейер
  тестируется без сети и без денег.
- **Contract.** Записанные (VCR-стиль) реальные ответы прогоняются через Pydantic-схему —
  ловим изменение формата на стороне API.
- **Live smoke.** Один реальный вызов на CI по расписанию (не на каждый PR),
  проверяет доступность модели, работу кеша и схемы.
